# Отчёт о безопасности: новая архитектура

## Проблемы в исходном HTML

1. `LS_USERS = 'users'`: браузерная база аккаунтов, функции `getUsers()`, `saveUsers()` и сравнение паролей на клиенте. Подмена данных и чтение паролей другим JavaScript того же origin.
2. `AdminAccess.authorized` переопределялся в загруженном HTML и проверял `user.isAdmin`; злоумышленник мог изменить локальную роль и данные. В конце файла есть отдельные локальные полномочия boss, смена чужих паролей в localStorage и демонстрационные чаты.
3. Бан/кик через изменение localStorage и `localSessionVersion` не отзывали настоящую удалённую сессию.
4. Участки UI строили HTML через `innerHTML` с включением ников; это создавало риски DOM XSS, особенно в админке.
5. Сохранение и просмотр чатов/записей зависели от нестандартного локального WebSocket-сервера; без его исходников нельзя подтвердить server-side authorization.

## Что устранено в новой версии

- Убраны `LS_USERS`, локальные пароли, доверие к `isAdmin` и фиктивный локальный кабинет начальника.
- Email+password через Supabase Auth, email verification и password reset. Нет собственных хешей или самописных JWT.
- Структурированный React-рендер без небезопасного `innerHTML` для пользовательских строк.
- RLS включён на всех пользовательских таблицах. `auth.uid()` определяет владельца данных; простой клиентский флаг больше ничего не решает.
- `GRANT UPDATE (username, bio, avatar_path)` ограничивает изменение профиля: роль и бан нельзя менять по PostgREST.
- Управление ролями/банами только через `SECURITY DEFINER` RPC с перепроверкой `auth.uid()` и роли в БД, исключением самого себя/начальника, журналом аудита.
- Дружба подтверждается только получателем запроса в `accept_friendship`.
- Сообщения доступны только принятым друзьям, поля `sender_id` и `created_at` не задаются клиентом, длина текста ограничена, действует DB anti-spam throttle.
- WebRTC Broadcast приватный, контролируется RLS по topic `call:<friendship_id>`.
- Storage проверяет владельца файла, его размер и MIME type.
- На Vercel заданы HTTP security headers и строгий `script-src 'self'`.

## Остаточные риски и действия до публичного релиза

- Security-headers сами по себе не доказывают отсутствие XSS; проведите DAST/SAST и проверку зависимостей.
- Текущая Auth session сохраняется через Supabase JS client и хранится в браузере. CSP снижает XSS-риск, но не заменяет аудит стороннего кода; при особо строгой модели угроз стоит перевести auth на cookie-based SSR (например, Next.js + `@supabase/ssr`).
- Регистрация требует внешней защиты от ботов: настройте SMTP, rate limits и интеграцию CAPTCHA. Одноимённые пользовательские ники защищены уникальным индексом без учёта регистра.
- Аватар Storage публичный; не загружайте туда конфиденциальные материалы. Публичные аватары — осознанная функция.
- Нельзя гарантировать доставку звонков без TURN. Участники WebRTC обычно узнают сетевые кандидаты друг друга через ICE.
- Защитные меры от публикации злонамеренных сообщений включают React escaping; для модерации оскорблений/спама нужны правила и отдельные механизмы жалоб.
- Блокировка доступа к существующему realtime-каналу может вступить в силу с задержкой до переподключения или смены JWT.
- Проверки здесь статические; в производственной среде нужны проверка политик RLS с разными JWT, нагрузочные тесты и мониторинг ошибок.
